# 后端开发状态

> 更新日期：2026-09-21。

## 分层约定

- `app/api/`：FastAPI 路由、Pydantic 输入校验、权限与响应封装。
- `app/services/`：业务规则、统计、报表、外部系统协调。
- `app/database/`：SQLite repository、SQL Server/PDM 客户端和 Excel 只读适配。
- `app/workers/`：应用生命周期内的单进程后台工作线程。

## 2026-10-12 模型用量明细

- 沿用 `llm_usage_totals` 累计 API，新增 `llm_usage_calls` 与 `llm_usage_tracking`，升级只建新表、保留旧累计；每次调用的明细与累计在同一 SQLite 事务中写入，统计写入失败只记录日志，不影响原分析结果。
- 报表和告警的实际模型请求统一记录场景、配置模型、按业务时区转换的请求开始时间、HTTP 耗时、响应返回/请求失败，以及供应商 `usage` 中的输入、输出、总量、缓存输入和推理输出。缓存/推理分项不重复计入总量，总量缺失时仅在输入和输出都有效时相加。
- 管理员 `GET /api/v1/llm-usage/report` 支持含首尾日期的最长 366 天区间、day/month 粒度、场景筛选及每页最多 100 条明细。区间概览、周期聚合、场景/模型分布和分页明细共用一个 SQLite 读事务，分页不改变汇总。
- 无调用日期显示零；有调用但未返回用量显示未知；明细启用前的无记录周期显示未记录。旧版累计不归入任何日期。接口响应不包含提示词、模型正文、供应商地址或凭据；“响应已返回”不等于分析内容校验成功。

- `data_source: production` 引用现有生产数据源；数据库连接、密码及全局功能开关继续由环境配置管理，不写入 JSON。JSON 沿用已确认的一块气表、DH01/DH02/DH03 三块电表及告警起始时间，不改变单位、统计范围或开启状态。
- `config.py` 在启动时通过现有 Pydantic 读取并校验 JSON，将默认设备的生产编号、能耗绑定、告警设备编号和起始时间作为 `Settings` 默认值。无效 JSON、重复编号、无效产线引用、无效或重复仪表编号均明确报错，不静默切回 Cutter01。
- `DEVICE_CONFIG_PATH` 可指定文件，默认路径如上；相对路径按项目根目录解释，与启动工作目录无关。JSON 随既有 Docker 和源码部署包携带，修改后重启生效。

## 2026-09-14 实现状态

### 车间确认更正

- 工人撤销：`POST /api/v1/workshop/tasks/{task_id}/revoke`。
- 管理员更正：`POST /api/v1/workshop/tasks/{task_id}/correct`。
- 历史日报中 `scope_machine_no` 缺失时仍可正常定位原报表并更正，不得因新字段缺失阻断旧数据。
- 确认变更继续保留审计记录，不写回生产任务表。

### 切割文件批量推送

- `POST /api/v1/cutting/dispatches/batch` 一次创建 1–20 个任务，支持直接携带 PDM 文档、版本和路径快照，也兼容历史 `download_id`；每个文件独立携带材质、厚度和数量。
- 直接派发会在建任务时复核 PDM 当前版本和路径，执行时按“下载、校验、上传、指派”推进，不要求用户预先保存文件。
- 服务返回创建、重复和失败的分项结果；前端对新创建任务顺序执行，避免同一魔盒通道并发推送。
- 单个和批量建任务均由服务端复核标准文件名：非标准名或标准名参数不符时要求显式人工确认；材质和板厚不能为空或无效。
- 文件参数识别按名称开头首次出现的“3 位板厚 + 材质代码”提取，板厚除以 10；中间产品编号不限定长度或固定 `C`，尾部序号和附加字母不参与校验。前后端保持一致，例如 `P403P080A601B.gen` 识别为 AH36、8.0 mm。
- 活动任务的重复判断与插入在 SQLite `BEGIN IMMEDIATE` 短事务内完成；同一文件版本和机床的并发建任务只允许一个创建成功，其余返回同一条重复任务。
- `GET /api/v1/cutting/dispatches/{dispatch_id}` 可读取单项最新状态；前端仅在文件版本、路径、机床、材质、板厚、数量一致且 `can_execute` 时继续已有任务。上传结果未知的任务由服务端禁止重复上传，需人工核对魔盒。
- 推送成功后 `FileDownloadService.delete_after_push()` 删除对应实体文件，下载记录、清理原因和推送任务标识保留至统一派发保留期。
- 清理失败不回滚已成功的远端推送，而是以 `local_file_cleanup.error` 警告管理员。
- 文件保存仍复核当前 PDM 文档版本和 `FilePath`；同版本存在历史物理文件记录时，使用查询已稳定选出的最新记录，不再仅因记录数量大于 1 拒绝重复保存。

### 智能分析缓存

- 领导、车间和设备报表接口返回 `analysis_source_version`，用于前端识别业务数据变化。
- `ReportAnalysisService` 对完整模型上下文进行稳定序列化和 SHA-256 计算，生成 `data_version`。
- SQLite `report_analyses` 按报表类型、日期和数据版本核对缓存；旧表自动补充 `data_version`。
- 同一进程内，同一版本的并发请求只调用一次模型；手动“重新分析”会替换该版本的缓存。

### 告警事件报告关联

- `GET /api/v1/alarms/incidents/page` 在当前事件分页内按 `pdf_report_id` 关联报告，附带 `report_status`、`report_error_message` 和 `report_view_url`，不受最近报告列表的 50 条限制；只有已完成且保存查看文件路径的报告返回查看链接。
- 仅扩展只读响应，不改变告警状态、计数、分页、报告生成或失败后解除关联并重试的机制；缺失关联记录不伪装为已归档。

### 报表自动化参数

- `GET /api/v1/automation/configuration` 返回自动化、扫描、重试和 SMTP 配置，只返回密码是否已配置。
- `PUT /api/v1/automation/configuration` 验证端口、超时、发件人及 TLS/SSL 互斥规则，原子写入 `data/settings.env`。
- 密码留空会保留运行配置文件中的最新值；保存其他自动化参数不覆盖数据库配置。
- 参数保存后通过共享的不可变配置快照切换：新扫描、新邮件发送及新重试使用新参数；已在运行的操作用旧快照完成，无需重启服务。数据库配置仍需重启。

### 统一数据保留

- `RetentionWorker` 在服务启动时执行一次，此后按 `RETENTION_CLEANUP_INTERVAL_HOURS` 周期运行；部署仍保持单 Uvicorn worker。
- 默认保留期：报告文件、生成任务、车间任务快照和孤立确认365天，分析版本90天，告警记录及关联告警报告按发生时间30天（仅已解除告警可清理），非活动派发与已清理下载记录365天，确认和权限审计730天；对应天数设为0可单独关闭。
- 告警按 `first_start_time` 起算，缺失时使用 `first_seen_at`；严格超过30天且已解除才删除，不从解除时间起算。共享告警报告必须所有仍存在的成员均已解除且过期；生成失败后已解除当前关联的报告仍按保存的告警 ID 核对。历史回查跳过已过期且已解除、未在本地保存的源事件，避免清理后重复补录和生成报告；已保存的未解除事件仍接收解除更新。普通生产报表保留期保持365天。
- 仅删除终结状态：运行中报告、待发送邮件、活动告警、活动派发以及当前确认状态不受影响。
- 报告和告警文件在删除元数据时写入 `retention_file_deletions`，物理删除成功后移除队列项，失败则保留错误和尝试次数供下一轮重试。
- 文件路径必须位于 `reports/`，越界路径和符号链接不会被清理任务跟随。

## 验证要点

- 涉及任务确认时覆盖旧日报、重复确认、撤销/改派和审计。
- 涉及文件推送时覆盖批量上限、重复任务、顺序执行、完整性校验与成功后清理。
- 涉及分析时覆盖数据版本稳定性、业务数据变化、强制刷新和并发合并。
- 涉及运行配置时覆盖密码不泄漏、空密码保留、其他配置保留、文件权限和输入校验。
