# 后端开发状态

## 分层约定

- `app/api/`：FastAPI 路由、Pydantic 输入校验、权限与响应封装。
- `app/services/`：业务规则、统计、报表、外部系统协调。
- `app/database/`：SQLite repository、SQL Server/PDM 客户端。
- `app/workers/`：应用生命周期内的单进程后台工作线程。

- 管理员更正：`POST /api/v1/workshop/tasks/{task_id}/correct`。

### 切割文件批量推送

- `POST /api/v1/cutting/dispatches/batch` 一次创建 1–100 个任务，支持直接携带 PDM 文档、版本和路径快照，也兼容历史 `download_id`；每个文件独立携带材质、厚度和数量。
- 直接派发会在建任务时复核 PDM 当前版本和路径，执行时按“下载、校验、上传、指派”推进，不要求用户预先保存文件。
- 服务返回创建、重复和失败的分项结果；前端对新创建任务顺序执行，避免同一魔盒通道并发推送。
- 单个和批量建任务均由服务端复核标准文件名：非标准名或标准名参数不符时要求显式人工确认；材质和板厚不能为空或无效。
- 文件参数识别接受已确认的 `P/S/W/L/Z` 前缀，按名称开头首次出现的“3 位板厚 + 2 位材质代码”提取，板厚除以 10；材质代码不设值域白名单、不映射牌号，保持原字符填入、保存并上传。中间产品编号不限定长度或固定 `C`，尾部序号和附加字母不参与校验。前后端保持一致，例如 `P403P080A601B.gen` 识别为 A6、8.0 mm，`S803C320B001.gen` 识别为 B0、32.0 mm；加工参数被修改时仍需人工核对确认。
- 活动任务的重复判断与插入在 SQLite `BEGIN IMMEDIATE` 短事务内完成；同一文件版本和机床的并发建任务只允许一个创建成功，其余返回同一条重复任务。
- `GET /api/v1/cutting/dispatches/{dispatch_id}` 可读取单项最新状态；前端仅在文件版本、路径、机床、材质、板厚、数量一致且 `can_execute` 时继续已有任务。上传结果未知的任务由服务端禁止重复上传，需人工核对魔盒。
- 推送成功后 `FileDownloadService.delete_after_push()` 删除对应实体文件，下载记录、清理原因和推送任务标识保留至统一派发保留期。
- 清理失败不回滚已成功的远端推送，而是以 `local_file_cleanup.error` 警告管理员。
- 文件保存仍复核当前 PDM 文档版本和 `FilePath`；同版本存在历史物理文件记录时，使用查询已稳定选出的最新记录，不再仅因记录数量大于 1 拒绝重复保存。

### 智能分析缓存

- 当前领导、车间和设备报表的后台刷新/分析周期为 300 秒，由 `REPORT_BACKGROUND_REFRESH_SECONDS` 控制；每轮以 `force=True` 独立调用模型，数据未变也重新生成，上一轮未完成时新轮次并行且不合并。默认报表页面通过只读 `/api/v1/analysis/latest` 读取同设备、同日期/月、同模型及提示词版本最近一次完成的默认分析，不因新数据或后台未完成而额外调用模型；每10秒检查已完成结果，每300秒检查报表源版本。自选区间、手动重新分析和导出保留原分析流程。已有部署显式设置为 600 秒的，需同步改为 300 秒并重启后端；前端需部署新构建。
- 领导报表刷新与分析分发使用独立线程，每个刷新轮次独立启动分析任务，完成后保存结果供页面读取；待处理月份不再互相覆盖。每个任务读取最新快照，分析失败独立记录，停止时拒绝新任务并在原5秒预算内等待已启动任务。

- 车间/设备消费者的数据刷新与分析分发分开；各轮次、各报表独立启动分析任务，不等待前一轮模型返回，不覆盖同类待处理轮次。设备任务携带同次刷新记录与任务能耗快照，车间按该任务日期读取。两类消费者复用 `ParallelAnalysisTasks` 管理并行任务、错误隔离和停止；已开始的阻塞调用仍沿用现有超时退出。

- 领导、车间和设备报表接口返回 `analysis_source_version`，用于前端识别业务数据变化。
- `ReportAnalysisService` 对完整模型上下文进行稳定序列化和 SHA-256 计算，生成 `data_version`。
- SQLite `report_analyses` 按报表类型、日期和数据版本核对缓存；默认后台轮次及默认页面手动重新分析的成功结果额外标记`display_scope`（设备编号）。只读接口从该范围读取最新完成结果，自选区间/汇总不发布到默认范围；失败不写入，更新期间旧结果可继续读取。旧表自动补充可空`display_scope`及索引，原记录保留；无法可靠区分的旧缓存不推测归类，升级后首次成功默认分析才进入新接口。
- 同一cache_key的更新在SQLite单条UPSERT中比较generated_at，只接受不早于已有记录的结果，防止并行模型调用较早生成的结果因延迟写入而覆盖较新缓存；不同轮次仍独立调用，普通页面继续复用缓存。
- 同一进程内，前台同版本并发请求只调用一次模型；手动“重新分析”会替换该版本的缓存，固定周期后台分析各轮独立。
- 每台设备的页面、导出和定时刷新共用一个分析实例，不同设备保持隔离。定时强制分析绕过缓存和同版本单飞合并，每一轮各自发起模型请求并记录用量；自选区间页面/导出读取精确缓存、前台相同版本请求合并的规则保持；默认页面只读已完成结果。
- 模型请求共用进程级容量池，默认并发10，配置范围1–10。固定周期报表分析通过既有 `generation_priority` 机制按前台同等容量入场，可使用全池名额，避免被原后台半数配额延误。告警等其他后台工作仍受半数配额与前台优先约束，已开始请求不抢占。已有部署显式配置4时需改为10并重启；本机与部署模板同步为10。
- 自选区间页面等待同设备同版本的非强制后台分析时，该任务尚未发出的模型请求继承前台排队优先级，可使用预留名额；页面取消/超时后撤回其优先级，保留独立后台任务。容量释放按实际入场类型计数。当前等待者共享一次生成的成功或失败；失败不持久化，后续重试可重新生成。
- 默认模型响应时限180秒，连接超时最多10秒；同版本等待与模型容量排队共用120秒累计预算，分析总预算为两者之和（默认300秒），包含数据准备、所有尝试与退避。嵌套调用和重试不重置预算，导出已有的更短预算继续优先；SQL/HTTP沿用协作截止检查和驱动/套接字超时，进行中的阻塞调用不强制中断。已有环境变量优先，本次不新增配置项。
- 报表和告警共用`request_llm_json`：仅HTTP429最多重试两次；优先解析Retry-After秒数/HTTP日期，否则按5/10秒加0–1秒随机延迟退避。退避前归还并发，等待每100ms检查取消和截止，下一轮定时任务独立；服务端要求的等待超出剩余预算时直接保留429失败，不提前重发。超时、其他HTTP错误及结果校验失败不自动重试。每次实际尝试分别沿用原用量记录，失败不会被后续成功抹去。
- `report analysis timing`日志按设备、报表类型/日期、请求编号记录`total_ms`、`prepare_ms`、`cache_ms`、`same_version_wait_ms`、`capacity_wait_ms`、`model_ms`、`retry_wait_ms`、`finalize_ms`，并记录缓存结果、后台来源、是否提升优先级、输入字符数及完成/异常类别。新增`analysis_id`及`model_attempts`关联各次`model HTTP attempt`的状态码、异常类别、耗时和清理后的供应商请求编号，以及`model request completed`的HTTP尝试总结果；分析最终结果仍以报表耗时日志为准。成功、缓存命中、取消与失败均留记录；仅记录统计与标识，不记录提示词、正文或密钥，不增加用量页面逐次明细。
- 报表模型失败明确区分排队、响应超时、认证、限流、接口状态码和连接错误；日志带设备、报表类型、日期及异常类别。失败不缓存，后续请求可以重新生成；导出仍允许交付确定性报表并明确标记AI不可用。
- 2026-10-13内网日志确认一次`POST /api/v1/analysis`的503来自`httpx.ReadTimeout`，堆栈位于等待模型HTTP响应头阶段，属于模型接口响应等待超时，不能归因为容量排队超时。日志未包含该请求的实际超时配置和完整耗时，模型负载或网络延迟仍需内网核查。三类报表共用HTTP边界的回归覆盖超时原因展示、失败后恢复与成功缓存复用。

### 统一数据保留

- `RetentionWorker` 在服务启动时执行一次，此后按 `RETENTION_CLEANUP_INTERVAL_HOURS` 周期运行；部署仍保持单 Uvicorn worker。
- 默认保留期：报告文件、生成任务、车间任务快照和孤立确认365天，分析版本90天，告警记录及关联告警报告按发生时间30天（仅已解除告警可清理），非活动派发与已清理下载记录365天，确认和权限审计730天；对应天数设为0可单独关闭。
- 告警按 `first_start_time` 起算，缺失时使用 `first_seen_at`；严格超过30天且已解除才删除，不从解除时间起算。共享告警报告必须所有仍存在的成员均已解除且过期；生成失败后已解除当前关联的报告仍按保存的告警 ID 核对。历史回查跳过已过期且已解除、未在本地保存的源事件，避免清理后重复补录和生成报告；已保存的未解除事件仍接收解除更新。普通生产报表保留期保持365天。
- `cutting_file_dispatch_status` 按文档 ID + 版本 ID 保存最近派发摘要（任务标识、状态、阶段、目标机床、创建/更新时间和成功时间），不参与明细保留期清理，不以外键关联可删除的派发记录。创建、状态转换与重启恢复在同一 SQLite 事务内同步摘要；初始化从尚存明细补齐，保留比剩余明细更新的摘要。目录文件状态读取摘要，派发记录仍读取原明细；摘要不参与任务执行授权或重复派发拦截。
- 仅删除终结状态：运行中报告、待发送邮件、活动告警、活动派发以及当前确认状态不受影响。
- 报告和告警文件在删除元数据时写入 `retention_file_deletions`，物理删除成功后移除队列项，失败则保留错误和尝试次数供下一轮重试。
- 文件路径必须位于 `reports/`，越界路径和符号链接不会被清理任务跟随。

## 验证要点

- 涉及任务确认时覆盖旧日报、重复确认、撤销/改派和审计。
- 涉及文件推送时覆盖批量上限、重复任务、顺序执行、完整性校验与成功后清理。
- 涉及分析时覆盖数据版本稳定性、业务数据变化、强制刷新和并发合并。
- 涉及运行配置时覆盖密码不泄漏、空密码保留、其他配置保留、文件权限和输入校验。
