# 技术决策记录

> 更新日期：2026-10-07。本文档只记录需要后续持续遵循的决策。

## D-001 分析缓存以业务数据版本为准

- 决策：对完整、规范化的分析上下文计算 `data_version`，不以页面局部计数或时间戳作为缓存依据。
- 原因：任何会影响分析的业务值变化都应产生新分析，键顺序变化则不应产生新版本。
- 影响：新增分析上下文字段时，必须同步纳入源版本计算并补测试。

## D-002 自动分析采用即时请求与后端单飞保护

- 决策：报表数据就绪后前端立即发起请求，查询条件或数据版本变化时取消旧请求；后端对同一缓存键的并发生成做进程内合并。
- 原因：减少等待对使用体验的影响，同时依靠完整数据版本、旧请求取消和后端单飞避免旧结果覆盖及同版本重复生成。
- 边界：后端单飞是进程内机制；当前架构依赖单 Uvicorn worker。

## D-003 批量推送采用“批量建任务，顺序执行”

- 决策：后端一次校验并创建最多 20 个推送任务，前端对成功创建项顺序调用执行接口。
- 原因：保留批量操作效率，同时降低魔盒上传/指派通道的并发风险，并能显示每个文件的独立结果。

## D-004 推送成功后删除实体副本，按策略保留审计记录

- 决策：远端推送和指派成功后删除对应下载文件；SQLite 记录在统一派发保留期内继续保存。
- 原因：避免本地副本无限增长，同时在统一派发保留期内保留可追溯性。
- 失败语义：本地清理失败是警告，不将已成功的远端任务改回失败。

## D-005 运行配置持久化与自动化参数热生效

- 决策：报表自动化与 SMTP 参数继续使用 `data/settings.env` 持久化，保存后原子发布给 worker、自动化和邮件服务；数据库配置仍重启生效。
- 原因：自动化参数由共享的不可变配置快照切换，正在执行的操作继续使用其原快照，避免同一次发送混用新旧 SMTP 参数。
- 安全要求：原子写入、600 文件权限、保留其他受控配置、密码不回显。

## D-006 表格采用一套内容驱动列宽系统

- 决策：页面表格统一使用 `v-content-table`，列宽由内容和容器宽度计算，页面局部不另建一套固定比例。
- 原因：报表、文件、告警和设置表格的字段长度差异大，内容驱动更能保证短数值和时间完整可读。

## D-007 派发未知结果阻塞替代建单与盲目重试

- 决策：同文档、版本、机床存在活动或未解决远端任务时，建单和执行认领均在 SQLite 短事务中拦截；认领校验状态、阶段及尝试次数，执行与取消互斥。复用现有字段，不增加表结构。
- 失败语义：HTTP 200 且整数非零业务状态视为明确拒绝；超时、连接/协议异常、服务端失败、缺失上传 UUID 和非预期异常均保守视为结果未知。此语义依赖魔盒业务失败表示操作未生效的契约，投产前需核对。
- 恢复：上传、正在指派和正在取消被中断时禁止盲目重试；已保存上传 UUID 且尚未开始指派时可续指派。只有明确上传失败且无远端 UUID 的失败任务可释放建单范围。
- 保留：未解决及旧版未分类的失败任务不受普通派发保留期清理；必须核对远端后再处理。当前没有自动远端对账或人工解锁接口，不能以删除记录或手改失败阶段解除保护。
- 边界：保留成功/已取消任务允许后续业务建单的既有流程；仍依赖单 Uvicorn worker，不保证远端接口本身的幂等。

## D-008 告警回查只补数据，不推进增量边界

- 决策：告警仓储仅提交调用方传入的顺序扫描游标，不从事件最大 ID 推导边界；回查较高 ID 不证明中间记录已扫描。
- 事务：事件与扫描边界在同一事务提交或回滚；旧边界不能倒退已提交游标，重复回查不重复创建事件/报告。

## D-009 告警补查采用持久化轮转位置

- 决策：未关闭事件每轮最多回查 2000 条，按 ID 轮转；监控起始时间到当前时间的历史告警每轮补查一页，覆盖超过 24 小时的迟到数据。24 小时快速回查每轮最多 20 页。
- 事务：`alarm_sync_state` 增加两个默认 0 的回查位置，与事件和增量边界原子提交。监控时间窗改变时一起归零，进程重启保留位置；任一采集失败不推进位置。
- 边界：补查是最终一致，发现延迟取决于窗口内数据量、批大小和扫描周期；持续保持 SQL Server 只读。

## D-010 报表生成与自动化发送隔离，持久化断点补偿

- 决策：单 Uvicorn 进程内分别运行报表线程和自动化线程，后者负责调度、恢复扫描和邮件发送；慢报表不能占用邮件队列消费者。
- 恢复：启动后的首次扫描及周期扫描，每轮最多处理 100 条已预留未建单、已完成未入邮件队列、失败回调未落库的运行记录；建单前在 Unit of Work 内重新检查关联，重复邮件入队不回退已发送状态。
- 失败语义：认领、状态写入和业务回调异常分别记录，不退出消费者；邮件入队失败不能将已完成的报表改成失败。后台线程停止时健康接口返回 503 和线程存活状态。
- 边界：SMTP 发送结果未知时仍使用原重试策略，不承诺邮件恰好一次；外部调用依赖既有超时，停机等待超限会记录警告，Python 线程不做强制终止。

## D-011 邮件只重试明确失败，未知结果保留核对

- 决策：发送认领事务持久化稳定 Message-ID；SMTP 拒收结果保存到新增 `recipient_results_json` 字段，后续尝试仅携带拒收地址，已接受地址不会因部分失败再次发送。
- 失败语义：连接/认证等提交前失败和 SMTP 明确拒绝可按既有上限退避；提交中断、非预期异常以及 sending 状态重启均视为 unknown，不自动重发。QUIT 失败不能覆盖已收到的接受/拒收结果。
- 事务：邮件状态和自动化运行状态一起提交；SMTP 成功后数据库失败不能转为可重试。人工重试只允许 failed，使用短事务，活动、已发送和 unknown 均拒绝；未知结果及其报告不能被普通保留期清理。
- 边界：accepted 表示 SMTP 服务器接受，并非收件人已阅读；稳定 Message-ID 仅用于核对，不能保证接收端去重。unknown 需核对服务器日志，本轮未提供解除未知状态的人工入口，不得通过手改数据库盲目重发。此决策替代 D-010 中 SMTP 未知结果沿用旧重试策略的边界。

## D-012 配置读改写与运行发布共用锁

- 决策：复用既有原子写文件实现到 `runtime_settings_store`；数据库接口、自动化接口及 AutomationRuntime 使用同一个进程内 RLock。空密码基于最新已保存文件保留，自动化发布与磁盘写入在同一临界区完成。
- 失败：文件 flush/fsync 后以 600 权限原子替换，写入/同步失败保留旧文件并移除临时秘密文件；不发布未保存配置。
- 边界：仍按单 Uvicorn 进程部署，数据库重启生效、自动化热生效；多个独立进程或人工编辑同一文件不受此锁保护。

## D-013 无效数据源配置必须失败

- 决策：Settings 构造即校验数据源枚举，无效值禁止静默回退。生产环境的默认 demo 不视为授权，演示必须显式设置 APP_DATA_SOURCE_MODE=demo；非演示的兼容空模式继续按 APP_DEMO_MODE=False 选择 sqlserver。
- 导出：演示源生成的标准/自定义 HTML 与后续 PDF 使用显著的非生产提示，下载文件名带演示数据前缀；真实源不加此标记。

## D-014 告警报告恢复与执行所有权

- 决策：监控每轮使用独立 owner，并以本地非重入锁限制同一 Service 并发执行；后台每 60 秒续期 600 秒租约，失效 owner 不允许续租复活。采集入库、报告预留、完成及失败均在短事务内检查当前租约。
- 恢复：取得租约后每轮最多恢复 100 个遗留 generating 报告，将其标记中断失败并释放事件关联；后续通过原 emission_key 复用报告 ID，重新生成。旧表新增可空 execution_owner 字段，旧 generating 记录也能恢复。
- 文件：同一报告的不同尝试使用独立文件名；迟到渲染不能覆盖新文件。预期生成失败清理 HTML/PDF/临时文件，失去执行权后的已返回产物只清理自己的尝试，清理失败留日志。
- 边界：失去租约后停止后续阶段和提交，正在执行的外部调用暂不能强制取消；仍依赖单进程部署。硬崩溃时尚未登记的尝试文件可能成为孤儿，后续文件保留策略需覆盖；数据库状态恢复不依赖这些文件。

## D-015 业务生产日与事件时间分离

- 决策：继续采用现有 OP_DATE 优先、无效/空值回退 START_TIME 日期的源筛选口径；查询结果将该业务日作为独立 production_date 贯穿 SummaryBaseRecord、WorkshopRecord 和 EquipmentRecord。production_time / production_end_time 保留实际事件时间，不再为缺失的开始时间伪造午夜时间。
- 归组：领导日/月汇总、设备分日、车间趋势统一按 production_date；前端审计/纠正请求与任务按日计数使用同一业务日。没有新字段的旧响应/手工领域记录才兼容回退开始日期。
- 快照：SQLite workshop_report_items 新增 production_date，旧快照按其父单日日报日期回填，保留原时间、确认与审计。查询、快照和 AI 证据同时携带业务日与事件时间，业务日更正必须改变分析源版本。
- 边界：能耗区间仍按实际开始/结束时间计算；不调整设备范围、长度单位或源库写入规则。此决策替代开始时间分日的旧口径，真实 SQL Server 跨日数据仍需现场核对。

## D-016 自定义报告完整指标与展示上限分离

- 决策：报表流水线消费完整单次查询的结果流，按现有 sum/avg/min/max/count 口径计算指标；count 保持统计全部结果行，其他聚合忽略空值及非数值。明细和图表只保留 report_max_detail_rows 范围，任务数记录完整查询行数。
- 读取：SQL Server 沿用取消游标与连接上下文，每批最多 500 行；Excel 沿用其受锁保护的缓存 SQLite 连接，每批最多 500 行。查询预览复用结果流，达到上限立即关闭迭代器，不扫描其余结果。
- 展示：超过上限的 HTML/PDF 源模板明确标注完整查询行数、指标范围及明细/图表范围。展示顺序沿用查询返回顺序；需要稳定顺序的自定义查询应显式指定 ORDER BY。
- 故障：读取失败不返回部分指标，不生成看似成功的截断汇总；退出时关闭游标并释放连接/Excel 锁。
- 边界：没有改变源查询自身的 TOP、聚合或筛选语义，完整指该查询的全部返回行。仍需扫描完整结果；Excel 源文件缓存本身仍占用内存，整项期限、并发容量与真实 SQL Server 吞吐待 P1-13 验证。

## D-017 调度准备与邮件发送分别消费

- 决策：ReportWorker 保持单 Uvicorn 进程约定，报表生成、自动化恢复/调度准备、邮件队列分别使用一个线程。车间源查询不占用邮件消费者，阻塞 SMTP 不占用调度线程。沿用原仓储事务认领与唯一约束，不增加并行邮件发送者。
- 故障：邮件认领/落库异常在消费者循环记录并等待原轮询间隔；调度恢复和扫描仍分别隔离异常。健康接口补充 email_alive，邮件线程停止时返回 503。
- 生命周期：部分启动失败停止已启动线程并继续抛出原错误；未启动线程不执行 join。所有线程共享 5 秒关闭等待期限，超时记录仍存活的线程名称。
- 边界：关闭信号不能强制打断正在执行的外部调用；单次 SMTP 的长期阻塞仍会阻止后续邮件，整项超时及队列积压观测继续归 P1-13/P1-01。

## D-018 能耗快照刷新与跨日结算

- 决策：单日查询与月份补采使用统一快照刷新条件。无快照、时间戳无效/时钟倒退、达到配置 TTL 均重新计算；当天 TTL 上限仍为 60 秒，历史日使用现有 ENERGY_REPORT_SNAPSHOT_TTL_SECONDS。已保存部分结果不再被月补采永久跳过。
- 结算：带 is_today 的旧快照跨到历史日后立即刷新，不受剩余 TTL 限制；此处只消除午夜缓存障碍，真实边界样本迟到仍由后续刷新补全。
- 保护：单日和月份计算均按小时起点检查已有有效值，新响应若缺少任一已知有效小时，不覆盖原快照；完整新结果可按原口径更正数值。不写入全空的月份补采结果。
- 边界：月份视图仍读取已保存数据，刷新由现有后台调度触发。后台失败仍需持久化月份队列及退避，不能把此快照修复等同于 P1-11 全部完成。

## D-019 能耗历史月份队列持久化

- 决策：energy_history_queue 按仪表/账号/换算配置与采样规则的哈希及月份唯一保存，复用 EnergyReportRepository 的连接和短事务。请求插入采用冲突忽略，不重置已有失败退避；源账号密码不进入哈希或队列。
- 认领：BEGIN IMMEDIATE 选择已到期任务，按到期时间优先、同时间月份从新到旧。每次生成独立 claim_token，重排仅接受当前 running 认领；启动时恢复当前来源遗留 running，不依赖内存月份集合。仍要求单 Uvicorn 进程且只启动一个历史消费者。
- 恢复：某月同步异常只推迟该月份，从 30 秒指数退避到最多 3600 秒，其他月份不清空。队列只保存异常类型，详细异常留原日志。完成落库失败先重试同一完成写入，不重复查询；进程崩溃由启动恢复。
- 周期：正常/空/部分响应都保留后续复查；历史月份周期为快照 TTL 且不低于 60 秒，当前月为 60 秒。退避期间不报告为正在同步，到期/执行中才报告 syncing；未来月份不入队。由此已保存部分数据即使用户不再次打开页面也可补全。
- 边界：队列持久化消除重启和失败丢任务，真实平台大范围周期查询吞吐、全项期限与后台停止期间的在途取消仍归 P1-13。历史请求月份会继续按配置周期复查。

## D-020 自动报表错过周期逐次补齐

- 决策：未另选业务策略时，采用推荐的逐周期补齐。下一次运行时间从该次原定 scheduled_for 推进一个周期，不从当前时刻跳转；报表日期按原定时间解析，保留运行记录作为补齐依据。补齐任务仍沿用计划的报表与邮件设置。
- 容量：每轮最多扫描现有 10 个名额，每条计划每轮预留一个周期，后续由正常扫描继续补齐；按 last_run_at 优先、再按 next_run_at 排序，避免一组古老积压持续占满名额。报表和邮件仍各一个消费者。
- 原子性：继续使用原 reserve_run 短事务和周期唯一约束，时钟推进与运行记录预留共同提交/回滚。同一旧计划快照并发预留只允许一个成功；建单中断由已有 reconcile_runs 恢复。
- 异常：单条计划格式/预留/建单异常只记录该计划，不终止本轮其余计划。API 已有启用/停用与人工触发边界不变。
- 边界：部署前应核对积压周期，补齐报表会沿用已配置的邮件发送。旧版本已越过且未记录的周期不能凭当前计划还原，应按历史计划和运行记录人工核对；不生成推测性历史记录。

## D-021 SQL 请求取消的执行身份与会话归属

- 决策：保留客户端 X-Request-ID 用于返回、日志和取消路径，但每个 HTTP 请求创建独立内部执行 ID；ContextVar 与 SQL 游标注册只使用内部 ID，结束一条同名请求不会删除另一条记录。
- 归属：optional_user 完成真实会话校验后，将用户 ID 与会话 Token 的联合摘要绑定到执行记录；取消接口必须 require_user，按相同用户/会话摘要寻找目标，不提供跨用户或跨会话取消。原始 Token 不保存到注册表。
- 时序：中间件保存会话 Token 的单独摘要；认证前到达的取消只允许已认证取消端匹配该会话摘要，后续注册的游标发现取消状态立即拒绝执行。无会话/无认证的目标不参与这种取消。
- 冲突：同一会话并发使用同一客户端 ID 的第二个已认证请求返回 409，避免取消含义不确定；不同用户/会话的同名请求各自独立。取消端继续统一返回 accepted，不暴露他人正在运行的请求。
- 验证：真实 FastAPI 请求穿过中间件、认证依赖、同步查询线程及取消接口，验证其他用户/同用户另一会话不可取消、原会话取消返回 499、重复请求拒绝与游标释放；另覆盖认证前时序和完成生命周期。
- 边界：此机制针对 HTTP 内同步 SQL 的取消，后台报表/LLM/PDF 全项停止另属 P1-13；未登录的 SQL 工作台 Token 查询不能使用登录会话取消端。

## D-027 AI 分析容量与并发边界

- 决策：LLM 请求不截断事实上下文；序列化后的用户输入超过 LLM_MAX_INPUT_CHARS（默认 500000）直接拒绝，避免静默丢失表格。模型返回内容超过 LLM_MAX_OUTPUT_CHARS（默认 50000）视为不可展示结果。告警和报表分析共用容量控制器。

- 验证：输入/输出超限在网络前后被拒绝，共享槽位限制并发，排队取消释放资源，配置范围校验；694 项后端回归通过。
- 边界：当前输入/输出限制基于序列化字符数而非模型 tokenizer；客户端响应体总时限不等于可强制终止服务端推理，LLM 跨调用预算、Chromium 终止和跨进程并发仍需按 D-030/D-031 之外的边界继续评估。

## D-029 报表流水线的协作式停止

## D-030 PDF 渲染进程级硬期限

- 决策：生产启动的 `PdfService` 使用 `PDF_RENDER_TIMEOUT_SECONDS`（默认 120 秒）在独立 Chromium 子进程中渲染。父进程以 100ms 级别轮询等待，超时、HTTP 取消或服务异常时终止并回收子进程，再删除临时 PDF；只有子进程正常退出且临时文件存在才允许原子发布。
- 兼容：未配置进程级期限的 `PdfService()` 仍走原有直接 Playwright 路径，保留测试替身和本地调用的行为；应用主生命周期显式传入生产期限。PDF 排队名额和单渲染锁仍在父进程统一控制。
- 边界：子进程内的 `page.pdf` 无法被 Python 线程安全中断，因此由父进程终止整个渲染进程；子进程异常只返回通用失败，详细堆栈留在其日志。LLM 与 SQL 的单次调用仍依赖各自客户端/驱动超时。
- 验证：模拟卡住的渲染进程确认超时必定 terminate；直接路径仍验证 Chromium 关闭、临时文件清理、容量释放和页脚；配置范围和下载接口回归通过。
- 回收补充：成功、异常退出、超时和取消统一进入 finally；已停止的 multiprocessing.Process 显式 close，释放原生句柄。POSIX 进程组清理不再因渲染主进程已退出而跳过，SIGTERM 后仍向自有组发送 SIGKILL，清除拒绝 TERM 的同组后代。沿用项目现有进程组/Windows taskkill 方案；参考 psutil 成熟进程树实现后未新增依赖，因为仅靠临时父子枚举也会在父进程退出后丢失后代关系。
- 真实验证：`test_pdf_process_cleanup.py` 的 3 项 spawn 进程回归在修复前复现主进程异常退出/超时遗留后代及正常渲染不关闭句柄，修复后全部通过。当前 macOS Playwright/Chromium 实测正常生成、2 秒超时、在途取消和后续再次生成，观察到 3～6 个真实进程；四种路径的已观测后代均退出，自有组为空、句柄关闭、临时文件消失且容量可再次获取。超时约 2.08 秒返回，后续报告约 0.61 秒完成。2026-10-06 全量后端 785 项通过，有一条既有测试客户端弃用警告；本轮未改前端。
- 验证边界：Playwright 在 POSIX 会将浏览器放入另一个进程组，浏览器回收也依赖驱动的关闭/断连处理；当前实际 Chromium 测试验证了该路径，不能推导为任意脱离会话后代都由本组信号覆盖。Windows taskkill、驱动崩溃和生产规模仍需在部署环境验收；本次没有修改 Playwright 私有实现或新增系统级进程托管机制。

## D-031 LLM 响应体总时限

- 决策：LLM 使用 `LLM_TIMEOUT_SECONDS` 作为一次完整 HTTP 响应的墙钟预算。真实 httpx 客户端采用流式读取，在每个响应块之间检查剩余时间，并把首包等待与响应体读取纳入同一预算；超时抛出专用 `LlmRequestTimeout`，由既有分析失败路径处理。告警分析和标准报表共用该传输边界。
- 兼容：只有 `post()` 的旧适配器和测试替身继续走兼容分支；生产 httpx 客户端优先使用 `stream()`。两种路径都将已解析响应交给用量记录，不对已消费的流再次调用 `response.json()`。LLM 容量槽位仍由外层 `llm_capacity` finally 释放。
- 容量：标准/告警分析的响应体按解码后字节数在读取中限制为 `12 × LLM_MAX_OUTPUT_CHARS + 65536`（容纳 JSON Unicode 转义及有界供应商元数据），超限关闭响应且不返回部分结果；模型正文继续单独检查字符上限。同版本锁等待和全局并发槽等待均检查排队期限、请求取消及报表剩余预算，退出只回收本等待者的引用/名额。
- 边界：HTTP timeout 取模型上限和报表剩余预算的较小值，在块间与解析后检查总预算/取消；不能即时终止正在阻塞的单次 socket 读取，也不能终止远端推理，因此该预算是协作检查，不能宣称进程级硬期限。只有 post() 的兼容适配器在返回后检查容量，生产流式路径在读取中检查。
- 验证：实际分析服务并发测试覆盖同版本等待超时、取消、报表预算耗尽、引用释放及后续缓存/强制刷新；真实 httpx MockTransport 覆盖响应超限提前停止、取消关闭、请求 timeout 收紧及标准/告警分析成功记录用量；旧 post 替身继续回归。
- 配置服务实测：2026-10-06 当前已配置 LLM 的 `/models` 返回 200；用虚构的两条任务和六项事实调用实际 ReportAnalysisService/供应商，约 2.21 秒完成四段非空文本解析、SQLite 分析缓存和用量记录；第二次同版本请求命中缓存，供应商仅调用一次，共享容量归零。诊断使用临时数据库，未发送生产数据或输出密钥。此结果只验证该服务一次正常分析与缓存，不证明所有报表/告警场景、异常状态、语义准确性或生产规模。

## D-032 后台报表跨查询总预算

- 决策：`ReportPipeline.run` 为每份后台报表建立 `REPORT_OPERATION_TIMEOUT_SECONDS`（默认 900 秒）的 ContextVar deadline。阶段检查在查询、统计、分析和渲染边界执行；SQL Server 建连和连接查询 timeout 动态取配置上限与剩余预算的较小值，预算耗尽抛出 `ReportOperationTimeout`，由报告 Worker 的既有失败和恢复路径处理。
- 范围：只对后台报表流水线生效；普通 HTTP 查询、SQL 工作台和独立 HR/文件数据源请求不共享该 deadline，避免把一个报表任务的预算错误泄露到其他请求。
- 边界：驱动已进入不可中断的单次调用时，Python 不能即时打断，只能依靠动态 query timeout 和下一阶段检查；能管平台请求已复用报表剩余预算，SMTP 和魔盒等非报表外部调用使用各自的会话/流程预算，真实大规模联调需要确认累计耗时和驱动行为。
- 验证：deadline 过期与 ContextVar 恢复、SQL/能管连接 timeout 截断、自定义报表扫描期限、配置边界及 702 项后端回归通过。

## D-033 SMTP 单次发送总时限

- 决策：`EmailService.send` 以现有 `SMTP_TIMEOUT_SECONDS` 建立一次发送的墙钟预算；SMTP 建连、TLS、登录和 `send_message` 前都会把底层 socket timeout 更新为剩余时间，发送完成后也收紧 QUIT 的等待。预算耗尽发生在服务器接受邮件前时记为可重试失败，发生在提交阶段之后仍沿用未知结果，不自动重发。
- 安全：不通过线程强杀 SMTP 调用，也不把超时后的服务器状态猜成成功；Message-ID、未知状态和人工核对流程保持不变。socket 不可访问的测试替身继续走原有 timeout 参数。
- 边界：单次 SMTP 会话有总时限，但多个邮件投递之间没有共享批次预算；设备或 SMTP 驱动已经接受请求后的执行无法由 Python 进程级强杀。
- 验证：覆盖发送结果分类、QUIT 异常、阶段预算耗尽、部分拒收和自动化邮件状态回归。

## D-034 魔盒派发流程共享总预算

- 决策：`CuttingDispatchService` 的上传、指派和取消分别建立 `MAGIC_BOX_OPERATION_TIMEOUT_SECONDS`（默认 180 秒）操作截止时间；`MagicBoxClient` 每次请求把自身 `MAGIC_BOX_TIMEOUT_SECONDS` 与操作剩余时间取较小值，并在请求和响应解析边界检查截止时间。超时沿用上传、指派和取消的结果未知语义，禁止自动盲目重试。
- 范围：总预算覆盖同步时间、上传/指派/取消请求和状态转换等待；本地文件准备仍有其独立下载超时。操作截止时间使用 ContextVar，不泄漏到普通 HTTP 请求或其他后台任务。
- 边界：无法强杀已进入魔盒设备执行的单次 HTTP/设备调用；需要在实际设备环境核对网关超时、重复请求和结果查询流程。
- 验证：`test_magic_box_service.py` 验证请求 timeout 按共享剩余预算收紧和预算耗尽的 504/结果未知分类，切割派发回归及 702 项后端测试通过。

## D-035 确定性报表与 AI 分析解耦

- 决策：后台报表生成将 `AnalysisUnavailableError` 限定在 AI 区域；模型未启用、超时、连接失败或输出不可展示时，确定性查询、统计、HTML/PDF 生成和自动化投递继续完成，报告状态为 completed，`ai_status=unavailable`。报告内使用明确的不可用提示，不生成规则或模型替代结论。
- AI 准备：领导区间报表的历史对比、车间日报/区间的前期及去年记录、设备日报/区间的模型输入恢复及历史对比，均放入只处理 AI 的回调。禁用 LLM 时不执行这些查询；准备失败记录异常并标记 unavailable，不把失败解释成历史零值，也不调用模型生成缺少历史上下文的结论。
- 边界：正文数据查询、必需的月度趋势、统计和渲染仍位于 AI 回调之外；这些失败会阻止报告发布。`ReportOperationTimeout`、`SqlRequestCancelled`、`ReportPipelineCancelled` 继续传播，不能被 AI 降级吞掉。独立智能分析 API 行为保持不变。
- 验证：`test_pipeline_ai_isolation.py` 的 33 项回归覆盖三类标准报表的默认日期/月度及区间路径，验证禁用时不查 AI 历史、历史失败/模型超时/无效输出仍生成真实 HTML，并逐节对比 AI 成功时的汇总、明细、图表与业务字段；六类必需查询失败均不发布文件，三种控制信号不降级。PDF 与实际 SMTP 投递仍按内网联调验收。
